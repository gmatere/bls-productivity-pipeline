How the data gets in

Re-running must handle files that were added, changed or removed, and must not reprocess anything already ingested. Filenames can't carry that, because pr.data.0.Current changes in place. So ingestion keeps a manifest — one Delta row per file holding its ETag, Last-Modified, SHA-256, size and status.

The headers are a hint; the hash is the proof. BLS builds its ETag from the publish batch, not the file contents — pr.data.1.AllData and pr.series returned the same ETag. A republish therefore moves the ETag on files that didn't change, and the hash check is what stops the whole batch being downloaded again for nothing.

Removed files are marked, not deleted: a file disappearing upstream is worth knowing about. The file list itself is read from the BLS directory page at runtime, so nothing is hardcoded and a new file is picked up without a code change.

403 is resolved the way BLS's access policy asks — a User-Agent carrying a contact address — and requests retry with exponential backoff on 429 and 5xx.

How it's modelled

LayerJob
Bronze Stores what the source sent, everything as text, one table per file. Only names are cleaned — BLS pads its headers to a fixed width inside a tab-separated file, and Delta rejects the space in the API's Nation ID. Values pass through untouched.
Silver Trims, types and asserts. series_id values are padded too — without trimming, WHERE series_id = 'PRS30006032' returns nothing and question 3 quietly has no answer. Expectations live here because this is the first layer that makes a claim.
Gold One table per question, nothing else.

SQL or PySpark

PySpark is primary and builds the Gold tables; Spark SQL is the documented alternative. They don't just look alike — the SQL file full-outer-joins its result for question 2 against the PySpark Gold table and counts the rows that disagree. The answer is zero.

Decisions that mattered

Q05 is the annual average, not a fifth quarter. pr.period lists Q01–Q04 as quarters and Q05 as AN AV. Question 2 asks for the largest sum "across all its quarters" — and including Q05 adds the average of four numbers to those same four numbers. Excluded, and carried through Silver as is_annual_average so the decision is visible where it's made rather than buried in a filter.

A green pipeline that produced nothing

dlt.read() reads the last committed version of a table, not the one being built in the current run. On a clean run every Silver table read an empty Bronze, produced zero rows, and the pipeline reported success. It fixes itself on the second run — which is what makes it dangerous. spark.read.table() resolves to the in-flight version.

Does it work on a clean deployment is a different question from does it work.

The label BLS had already written

A label composed from sector and measure rendered four different series identically. They differ by duration_code — percent change, index, level — which that label threw away. pr.series carries a series_title that distinguishes them properly. Enough of the documentation had been read to find the lookup tables; not enough to notice the answer was in the file already open.

The deduplication that wasn't added

There are no duplicates on (series_id, year, period) across all 92,328 rows. That's asserted with an expectation rather than papered over with a dropDuplicates(), which on a pair with differing values picks one at random and produces a wrong number with nothing to warn you.
